# Глава 1 — Терминал и shell: с кем вы разговариваете

Всю эту неделю вы живёте в чёрном окне с мигающим курсором. Эта глава объясняет, что это за окно, кто на самом деле отвечает на ваши команды и что происходит между нажатием Enter и появлением ответа.

Зачем это знать? Пока в голове нет модели, терминал — сборник заклинаний: они то работают, то нет, и непонятно почему. С моделью он становится предсказуемым инструментом — любую незнакомую ситуацию можно разобрать на части и понять, какая часть сломалась. Читайте главу после первого урока: она раскладывает по полочкам то, что вы видели на демо.

## Два способа разговаривать с компьютером

С компьютером можно общаться двумя принципиально разными способами.

Первый — **показывать пальцем**: навести курсор на файл, щёлкнуть, перетащить. Это графический интерфейс (GUI). Он гениален для разовых действий: не нужно ничего знать заранее, всё видно, всё подписано.

Второй — **говорить словами**: написать предложение на специальном языке и отправить его. Это командная строка (CLI). Порог входа выше: слова надо знать. Но у слов есть свойства, которых у жестов нет:

- Предложение можно **сохранить** и выполнить завтра — попробуйте «сохранить» последовательность из тридцати кликов.
- Предложение можно **переслать** соседу, вставить в чат, в инструкцию, в программу.
- Предложение можно **повторить** тысячу раз, на тысяче файлов, на пятидесяти серверах — без единого лишнего движения.
- Из коротких предложений можно **собирать длинные** — вы увидите это в главе 4, и это главный фокус всей недели.

Поэтому вопрос «GUI или терминал» — не про старое и новое. Это два инструмента с разной специализацией: GUI оптимизирован под разовые действия, CLI — под повторяемые и автоматизируемые. Серверы, сборка проектов, тестирование, деплой — всё это повторяемые действия, поэтому вся серверная индустрия говорит словами.

## Немного истории — чтобы интерфейс перестал казаться странным

Терминал выглядит архаично, потому что он и есть архаика — тщательно сохранённая.

В 1960-е к большим компьютерам подключали **телетайпы**: электрические печатные машинки. Вы печатаете строку — она уезжает в компьютер; компьютер отвечает — ответ печатается на бумаге. Никакого экрана: диалог строками, как переписка. Потом бумагу заменили экраном, но модель осталась той же — строки текста туда и обратно.

Окно, которое вы открываете сегодня, — это **эмулятор терминала**: программа, притворяющаяся тем самым железным устройством. Отсюда рудименты: сокращение `tty` (TeleTYpe) в выводе `ps`, «возврат каретки» в кодах перевода строки, привычка к строкам по 80 символов (ширина перфокарты).

Почему эту архаику не выбросили? Потому что модель «поток строк туда — поток строк обратно» оказалась настолько простой и универсальной, что на ней до сих пор стоит вся инфраструктура. Простое переживает модное.

## Терминал и shell — две разные программы

Это главное разделение ролей, без которого дальше будет каша:

- **Терминал** — окно. Он умеет две вещи: рисовать символы и передавать ваши нажатия дальше. Он *не понимает* ваши команды — вообще. Терминалы бывают разные (Windows Terminal, iTerm2, Terminal.app), и это чистая вкусовщина.
- **Shell** («оболочка») — собеседник. Это программа, которая работает *внутри* терминала: читает ваши строки, разбирает их и запускает другие программы. Shell'ы тоже бывают разные: `bash` (стоит на сервере курса и почти на любом Linux), `zsh` (по умолчанию на macOS). Для нашего уровня они одинаковы.

Проверить, кто ваш собеседник:

```bash
echo $0        # имя запущенного шелла
```

Аналогия: терминал — телефонная трубка, shell — человек на том конце. Заменить трубку — разговор не изменится; заменить собеседника — изменится, даже если трубка та же.

## Что происходит, когда вы жмёте Enter

Возьмём команду и проследим её путь целиком:

```bash
ls -l /tmp
```

1. Shell печатает **приглашение** (prompt) и ждёт. Мигающий курсор — это «я слушаю».
2. Вы печатаете строку и жмёте Enter.
3. Shell **режет строку на слова** по пробелам: получается список `["ls", "-l", "/tmp"]`. Этот список называется `argv` — он дословно, без изменений, доедет до программы.
4. Первое слово — **что запускать**. Shell ищет на диске исполняемый файл с именем `ls` (где ищет — следующий раздел).
5. Shell **запускает новый процесс** — живую копию программы (подробно о процессах — глава 3) — и передаёт ему остальные слова.
6. Программа работает; её вывод течёт в терминал.
7. Программа завершается и оставляет **код возврата** — число, по которому shell узнаёт, был ли успех (глава 4).
8. Shell снова печатает приглашение. Цикл замкнулся.

Ключевая мысль шага 4–5: shell — не переводчик «специального терминального языка», а **запускальщик программ**. Никаких «команд терминала» не существует: `ls`, `grep`, `python3` — это обычные файлы на диске, которые может запустить кто угодно. Shell лишь избавляет вас от необходимости указывать полный путь к ним.

## Где shell берёт команды: PATH

Спросим у самого шелла:

```bash
type ls        # → ls is /bin/ls
```

Вот и разгадка: `ls` — файл `/bin/ls`. Когда вы пишете `ls`, shell перебирает каталоги из специального списка — переменной `PATH` — и запускает первый найденный файл с таким именем:

```bash
echo $PATH     # /usr/local/bin:/usr/bin:/bin:...  (каталоги через двоеточие)
```

Отсюда расшифровка самой частой ошибки терминала. `command not found` означает ровно одно из трёх: вы опечатались; программа не установлена; программа установлена, но её каталог не в `PATH`. На неделе 2 научимся чинить третий случай — пока достаточно понимать, *что именно* сломалось.

Есть исключение:

```bash
type cd        # → cd is a shell builtin
```

`cd` — не файл, а **встроенная команда** самого шелла. Почему она не может быть обычной программой? Текущий каталог — личное свойство каждого процесса. Если бы `cd` была отдельной программой, она запустилась бы отдельным процессом, сменила каталог *себе* — и завершилась. А shell остался бы там, где был. Поэтому то, что меняет состояние самого шелла (`cd`, `export`), обязано быть встроенным. Это первый звоночек темы «у каждого процесса — своё», которая развернётся в главе 3.

## Анатомия командной строки

```bash
ls -l /tmp
```

- `ls` — команда;
- `-l` — **флаг** (опция): меняет поведение, здесь — «подробный формат»;
- `/tmp` — **аргумент**: над чем работать.

Соглашения, которые встречаются чаще всего: короткие флаги — дефис и буква (`-l`), длинные — два дефиса и слово (`--help`), короткие можно склеивать (`ls -la` = `ls -l -a`).

Важная честность: это именно **соглашения, а не закон**. Shell передаёт программе слова как есть — а уж как их толковать, каждая программа решает сама. Поэтому в мире Unix встречаются нарушители (`ps aux` — без дефиса, `find` — со своим особым синтаксисом). Вывод практический: если флаг «не работает» — не гадать, а читать справку *конкретной* программы.

## Как добывать помощь — главный навык недели

Профессионала от новичка отличает не количество команд в голове, а скорость, с которой он находит нужную. Три инструмента, в порядке применения:

1. **`команда --help`** — краткая справка, обычно один экран. Быстрый вопрос — быстрый ответ.
2. **`man команда`** — полная документация. Внутри: `/слово` — поиск, `n` — следующее совпадение, `q` — выход. Как читать раздел SYNOPSIS: в квадратных скобках — необязательное, `...` — можно повторять. `man` кажется многословным, пока не научишься искать в нём поиском — тогда он становится быстрее гугла.
3. **Поисковик/нейросеть** — когда вы не знаете, *как называется* нужная команда. Узнали имя — возвращайтесь к `man`: он про вашу версию программы, а интернет — про чью-то чужую.

И правило курса, повторим: вопрос «какой командой это делается» — легален всегда.
