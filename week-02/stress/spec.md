# stress.sh — спецификация

## Зачем спецификация

Стресс-тестировщик можно написать за десять минут «для себя», и он будет работать, пока вы помните, как его запускать. Но этот скрипт будет проверять автоматика (`check.sh`), а такими инструментами обычно пользуется не только автор. У инструмента, которым пользуется кто-то кроме автора, должен быть **контракт**: какие аргументы он принимает, что печатает, какими кодами завершается. Ниже такой контракт. Он нарочно точен, потому что автопроверка сверяет коды выхода и файлы, а не намерения. Это первое знакомство с тем, как устроены тесты и CI: машине нельзя ответить «ну почти работает».

Спецификация описывает, что должно получиться в конце, но не говорит, в каком порядке к этому идти и почему в ней каждый пункт. Об этом рассказывает `guide.md`: там скрипт растёт шаг за шагом, от четырёх команд с лекции до v2, и каждая потребность объясняется до того, как появляется конструкция. Если вы открыли спецификацию первой, начните всё же с `guide.md`, а сюда возвращайтесь как к справочнику.

## Интерфейс

```
stress.sh [опции] GEN A B
```

- `GEN` — генератор тестов: **исполняемый файл**, который запускается как `GEN SEED` и печатает тест в stdout. Одинаковый сид → одинаковый тест.
- `A` — эталонное решение (обычно тупое и медленное): читает тест из stdin, пишет ответ в stdout.
- `B` — проверяемое решение: тот же интерфейс.

На чём написаны GEN, A и B, stress.sh не касается: это могут быть скомпилированные C++-программы или Python-скрипты с shebang и правом на исполнение (гл. 1). Пути передаются как есть; имя без слэша (`gen.py`) означает файл в текущем каталоге, а не поиск в PATH (см. шпаргалку, «Переносимость»).

### Опции (v2)

| Опция | Смысл | По умолчанию |
|---|---|---|
| `-n N` | число тестов | 100 |
| `-s S` | стартовый сид: тесты идут с сидами `S, S+1, …, S+N−1` | 1 |
| `-t T` | лимит времени на **один** запуск решения, секунд | 2 |
| `-c CHECKER` | чекер вместо побайтового сравнения (см. ниже) | нет |
| `-o FILE` | куда сохранить контртест | `counter.txt` |
| `-h` | справка об использовании | |

Опции идут до позиционных аргументов (так работает `getopts`).

### Поведение

Для каждого сида по порядку:

1. `GEN SEED` → тест. Если генератор завершился с ненулевым кодом, это ошибка окружения: сообщение в stderr, выход с кодом 2.
2. `A < тест` → ответ A. Ненулевой код — вердикт **RE**; превышение `T` секунд — вердикт **TL**. (Да, эталонное решение тоже может упасть или не успеть, например если генератор выдал слишком большой тест. Это тоже находка: сообщите, чьё решение не отработало.)
3. `B < тест` → ответ B. Аналогично: **RE** / **TL**.
4. Сравнение. Без чекера ответы должны совпадать (рекомендуется `diff -B -b`: пробелы в конце строк и пустые строки в конце не считаются различием, так же смотрят судьи). С чекером вызывается `CHECKER тест ответ_B ответ_A`; код 0 — ответ принят, любой другой — вердикт **WA**.
5. Любой вердикт (WA, RE, TL) — остановиться: сохранить **тест** в `FILE`, напечатать сид, вердикт (именно слово `WA`, `RE` или `TL`) и то, что поможет разобраться (diff, stderr упавшего решения, сообщение чекера), завершиться с кодом 1.

Все `N` тестов прошли — сообщить об этом и завершиться с кодом 0.

### Коды выхода

| Код | Значение |
|---|---|
| 0 | расхождений не найдено |
| 1 | найден контртест (сохранён в `FILE`) |
| 2 | неверное использование (нет аргументов, файл не найден или не исполняемый, нет `timeout`) или отказ генератора |

Это протокол для программ: по коду 1 другой скрипт (или вы через `&&`) поймёт, что контртест есть, не разбирая текст.

### Вывод

- Ход работы (какой сид, что с ним) — в stdout; сообщения об ошибках использования — в stderr.
- **Цвет — только если stdout терминал** (`[ -t 1 ]`, гл. 3). В файле и в конвейере ESC-последовательностей быть не должно: `stress.sh ... | tail -1` обязан давать чистый текст.

### Интерфейс чекера

`CHECKER input output answer` — тест, проверяемый ответ (B), эталонный ответ (A). Код 0 — принято; иначе — отвергнуто, причина в stderr. Порядок аргументов совпадает с testlib — это библиотека, на которой пишут чекеры для большинства олимпиад и задач. Пример — `fixtures/chk.py`.

## Версии

**v1 (лаба, уроки 2–3)** — без опций: `stress.sh GEN A B`, 100 тестов с сида 1, побайтовое сравнение, остановка и `counter.txt` на первом расхождении, коды 0/1/2. Этого достаточно для задачи A.

**v2 (core, к концу недели)** — всё из таблицы опций: `-n`, `-s`, `-t` с вердиктом TL, вердикт RE, `-c`, `-o`, цвет только в терминале.

**v3 (bonus)** — на выбор, автопроверки нет:

- `-j J` — запускать `J` тестов параллельно (`&` и `wait`, или `xargs -P`). Осторожно с общими временными файлами: у каждого теста — свои.
- Автопересборка: если вместо исполняемого файла передан `.cpp`, собрать его в кеш (`g++ -O2`), а пересобирать только если исходник новее бинарника (`[[ src.cpp -nt bin ]]`). Это мини-make, написанный руками; на неделе 5 вы увидите, как он выглядит по-взрослому.
- Ужиматель: найдя контртест, попытаться уменьшить его (например, генератор принимает вторым аргументом максимальный размер) и сохранить самый маленький из найденных.

## Автопроверка

```bash
bash stress/check.sh путь/к/stress.sh            # на ноутбуке
check-stress                                      # на сервере (по умолчанию ~/week-02/stress.sh)
```

`check.sh` запускает ваш stress.sh на заглушках из `fixtures/`, маленьких решениях с заранее известным поведением (одно врёт при `n ≥ 7`, другое спит при `n == 3`, третье падает при `n == 4`; ещё две пары верных решений, одна с единственным ответом, другая с неоднозначным), и сверяет коды выхода, файлы и вывод с этой спецификацией. Что именно проверяется по пунктам, видно из вывода; каждый пункт помечен `v1` или `v2`. Второй этап проверки — контртест к задаче A (`task-a/counter.txt` рядом с `stress.sh`): скрипт сам собирает `slow.cpp` и `fast.cpp` и убеждается, что на вашем тесте они расходятся.

Проверяется **поведение**, а не текст: любая реализация, соблюдающая контракт, зачтётся.
