# Задачи недели 3 — тренажёр git

Все задачи, кроме двух последних, решаются в тренировочных репозиториях, которые собирает `setup.sh`. Для каждой написано, зачем она нужна, что дано, что должно получиться, с какой стороны подступиться и как самому понять, что готово. Подсказки спрятаны под спойлерами: сначала пробуйте сами, открывайте, когда застряли минут на пять. Команды в подсказках не решение целиком, а направление.

Рядом с `setup.sh` лежит `check.sh`. Он смотрит на состояние тренажёра и для каждой задачи говорит, сделана ли она, а если нет, то что именно не так: содержимое файлов он сверяет по хешам, историю читает через `log`, а следы ваших действий, слияние, stash, переходы между ветками, находит в `reflog`. Запускайте его после каждой задачи командой `bash check.sh`. Зачёт по задачам 1–7 снимается с сервера курса: преподаватель запускает тот же `check.sh` под вашей учёткой и смотрит на `~/git-practice` там. Поэтому тренажёр проходите на сервере (`ssh course-vps`), а если прошли на ноутбуке, повторите на сервере: во второй раз это быстро.

Две привычки сильно упрощают всю неделю. Первая: после каждой команды смотрите `git status` и `git log --oneline --graph --all`, пока картинка в голове не совпадёт с тем, что показывает git. Вторая: читайте сообщения git до конца, они написаны для вас, а не для галочки, и обычно заканчиваются подсказкой «чтобы сделать X, выполните Y».

## Подготовка

```bash
git --version                      # нужен 2.32 или новее
bash setup.sh                      # собирает ~/git-practice/{staging,conflict,messy,undo,bisect}
bash check.sh                      # пока всё красное: это список того, что предстоит
cd ~/git-practice
```

Если ваш редактор для git это vim и вы в нём не живёте, на эту неделю разумно переключиться на nano: `git config --global core.editor nano`. В nano сохранить и выйти это Ctrl+O, Enter, Ctrl+X. Редактор будет открываться на каждом `commit` без `-m`, на `rebase -i` и на `rebase --continue`, так что лучше, чтобы он не пугал.

Если что-то сломалось безнадёжно: `bash setup.sh --reset` пересобирает все пять репозиториев с нуля. Наработки в них пропадут вместе со следами, по которым `check.sh` узнаёт сделанное, так что после пересборки уже решённые задачи придётся пройти заново (во второй раз это быстро).

## 1. Хирургический коммит — `staging/`

**Зачем.** Коммит это единица, которой потом оперируют все остальные инструменты: ревьюер читает по коммиту, `revert` откатывает по коммиту, `bisect` ищет виновный коммит. Это работает, только если один коммит содержит одно осмысленное изменение. А работа так не устроена: вы чините баг, по дороге придумываете новую опцию, вставляете отладочный print, и всё это лежит в одном файле. Умение разложить одну кашу правок на несколько чистых коммитов и есть то, ради чего в git существует индекс.

**Ситуация.** В `staging/` один коммит и незакоммиченные правки в `topwords.py`. В них перемешаны три вещи: исправление бага (слова сравнивались с учётом регистра и знаков препинания), новая возможность (число слов передаётся аргументом) и две строки отладочного вывода `DEBUG`. Скрипт `test.sh` проверяет первые две вещи по отдельности.

**Что должно получиться.** Поверх первого коммита два новых: первый только с исправлением бага, второй только с новой опцией. Строк `DEBUG` нет ни в одном из них. `bash test.sh` показывает две галочки, `git status` чист.

**Как подступиться.** Начните с `git diff` и прочитайте его целиком, относя каждую изменённую строку к одной из трёх групп. С отладочным выводом проще всего разобраться сразу: он не нужен нигде, так что его можно просто удалить из файла руками, и тогда останется развести только две группы. Разводят их командой `git add -p`: git показывает изменения кусками (hunk) и про каждый спрашивает, класть ли его в коробку. Ответ `y` кладёт, `n` пропускает, `s` разрезает кусок на более мелкие, если между изменёнными строками есть нетронутые, `?` показывает все варианты. После этого `git diff --cached` показывает, что лежит в коробке, а `git diff` без флага то, что осталось на столе. Если в коробке ровно исправление бага, делайте коммит, затем кладите остальное и делайте второй.

<details>
<summary>Подсказка 1: кусок не режется, а в нём и нужное, и ненужное</summary>

Команда `s` делит кусок только там, где между изменениями есть неизменённые строки. Если две правки стоят вплотную, остаётся `e`: git откроет этот кусок в редакторе, и вы удаляете строки с `+`, которые не хотите класть (строки с `-` для этого превращают в строки с пробелом в начале). Сохранить, выйти, и в коробку уйдёт отредактированный вариант, а файл на столе не изменится.

</details>

<details>
<summary>Подсказка 2: положил в коробку не то</summary>

`git restore --staged topwords.py` вынимает файл из коробки обратно на стол, правки на столе при этом остаются. Можно начинать `git add -p` заново.

</details>

<details>
<summary>Подсказка 3: закоммитил не то</summary>

`git reset --soft HEAD~1` отменяет последний коммит, но оставляет его содержимое в коробке, а стол не трогает. Это самый мягкий reset: стикер ветки переезжает на родителя, и всё.

</details>

<details>
<summary>Подсказка 4: как проверить первый коммит отдельно, если на столе лежит и второе изменение</summary>

Спрячьте стол: `git stash` убирает незакоммиченные правки в сторону, после чего `bash test.sh` проверяет ровно то, что в коммите. `git stash pop` возвращает правки. Подробнее об этом в задаче 6, здесь просто попробуйте.

</details>

**Как понять, что готово.** `git log --oneline` показывает три коммита. `git show HEAD~1 --stat` трогает только `topwords.py`, а в `git show HEAD~1` нет слова `limit` и нет `DEBUG`. `bash test.sh` даёт две галочки, `git status` пуст. `bash check.sh`: раздел 1 без красного.

## 2. Конфликт, дважды — `conflict/`

**Зачем.** Конфликт при слиянии это не авария, а обычное событие в любой команде из двух человек. Страх перед ним держится на том, что непонятно, что означают маркеры и что делать после правки файла. Пройдя один конфликт медленно, с тестами под рукой, вы перестанете его бояться. А пройдя его вторым способом, увидите разницу между merge и rebase не на картинке, а на своей истории.

**Ситуация.** В `conflict/` две ветки. На `main` два коммита: `stats.py` научили переживать пустой ввод и дописали README. На `feature` один коммит: в `stats.py` добавили медиану. Обе правки легли на одни и те же строки. `test.sh` проверяет пять свойств, и ни одна ветка сама по себе не проходит все: посмотрите вывод тестов на каждой, прежде чем что-то сливать.

**Что должно получиться.** Сначала `feature` слита в `main` через merge, все пять проверок проходят, в истории есть коммит с двумя родителями. Затем слияние отменено и сделано заново через rebase: история прямая, тот же результат тестов, а первый вариант остался в альбоме под тегом `merged`, чтобы оба графа можно было сравнить.

**Как подступиться.** Посмотрите на развилку: `git log --oneline --graph --all`. Встаньте на `main` и выполните `git merge feature`. Git остановится с сообщением CONFLICT, а `git status` покажет файл как «both modified». Откройте `stats.py`: между `<<<<<<< HEAD` и `=======` версия `main`, между `=======` и `>>>>>>> feature` версия `feature`. Ваша задача не выбрать одну, а написать ту, в которой есть обе идеи: безопасные `min`, `max`, `mean` и строка с медианой. Уберите маркеры, запустите `bash test.sh` и прочитайте, что ещё не так. Когда все пять проверок проходят, `git add stats.py` и `git commit`: git сам предложит сообщение для merge-коммита. Посмотрите на граф и сохраните его.

Прежде чем отменять слияние, поставьте на него закладку: `git tag merged`. Коммит слияния останется в альбоме под этим именем: в конце вы сможете сравнить оба графа (`git log --oneline --graph merged main`), а `check.sh` увидит, что путь через merge был пройден. Теперь отмените слияние. Git запомнил, где была ветка до merge, в `ORIG_HEAD`; `git reset --hard ORIG_HEAD` возвращает `main` на место, а `git log --oneline --graph --all` снова показывает развилку. Перейдите на `feature` и выполните `git rebase main`. Снова конфликт, и снова те же маркеры, но теперь смысл сторон перевёрнут: `HEAD` это `main`, на которую вы перекладываете, а вторая сторона это ваш коммит с медианой. Разрешите так же, но вместо `commit` скажите `git add stats.py` и `git rebase --continue`. Потом встаньте на `main` и выполните `git merge feature`: это будет fast-forward, стикер просто переедет. Сравните новый граф со старым и обратите внимание на хеш коммита «add median»: он изменился, потому что rebase сделал новый коммит.

<details>
<summary>Подсказка 1: всё пошло не так, хочу назад</summary>

Пока конфликт не разрешён, `git merge --abort` или `git rebase --abort` возвращают репозиторий в состояние до команды. Это безопасно, пользуйтесь без стеснения.

</details>

<details>
<summary>Подсказка 2: тесты говорят, что медиана на пустом вводе не печатается</summary>

Посмотрите, что делает `median([])`: `s[mid]` при пустом списке падает. Разрешить конфликт значит не только склеить два текста, но и заставить их работать вместе: функции медианы тоже нужна защита от пустого ввода, как у среднего на `main`. Тесты именно для этого и даны.

</details>

<details>
<summary>Подсказка 3: что такое «ours» и «theirs» при rebase</summary>

При merge «ours» это ветка, на которой вы стоите, «theirs» это та, которую вливаете. При rebase git встаёт на целевую ветку и по одному накладывает ваши коммиты, поэтому «ours» это `main`, а «theirs» это ваш собственный коммит. Это главный источник путаницы при rebase; помните, что `HEAD` в маркерах это всегда то, куда накладывают.

</details>

<details>
<summary>Подсказка 4: после rebase --continue открылся редактор</summary>

Git предлагает отредактировать сообщение переложенного коммита. Ничего менять не нужно: сохранить и выйти.

</details>

**Как понять, что готово.** На `main` после обоих вариантов `bash test.sh` даёт пять галочек. В первом варианте `git log --oneline --graph` показывает ромб с merge-коммитом; во втором прямую линию, где «add median» стоит выше «readme: empty input is fine». `bash check.sh`: раздел 2 без красного.

## 3. Уборка в ветке — `messy/`

**Зачем.** Пока вы работаете, ветка это черновик: коммиты «wip» и «oops» нормальны, их никто не видит. Но pull request читает другой человек, и ему нужна не хроника ваших метаний, а история из двух-трёх шагов, каждый со своим смыслом. Перед PR ветку приводят в порядок командой `git rebase -i`, и это самое частое применение rebase в реальной работе.

**Ситуация.** В `messy/` ветка `feature` с шестью коммитами поверх `main`: `parser: read key=value lines`, `wip`, `fix typo in README`, `oops`, `parser: skip blank lines too`, `wip`. Код на вершине ветки работает (`bash test.sh` проходит), но история рассказывает не о парсере, а о том, как его писали.

**Что должно получиться.** Та же ветка `feature`, но из трёх коммитов с осмысленными сообщениями: один про чтение `key=value`, один про комментарии и пустые строки, один про README. Содержимое файлов на вершине ветки не изменилось ни на байт.

**Как подступиться.** Встаньте на `feature` и первым делом поставьте закладку на текущее состояние: `git tag before-cleanup`. Теперь что бы ни случилось, `git diff before-cleanup feature` покажет, изменилось ли содержимое, а `git reset --hard before-cleanup` вернёт всё назад. Посмотрите коммиты только этой ветки: `git log --oneline main..feature`, и для каждого `git show <хеш> --stat` или просто `git show <хеш>`, чтобы понять, к какому из трёх смыслов он относится. Составьте план на бумаге: какие коммиты сливаются вместе, в каком порядке, с какими сообщениями.

Затем `git rebase -i main`. Откроется список коммитов, самый старый сверху, и перед каждым слово `pick`. Это программа, которую git выполнит: строки можно переставлять, а `pick` менять на `squash` (слить с предыдущей строкой, объединив сообщения), `fixup` (слить, выбросив сообщение), `reword` (оставить, но изменить сообщение), `drop` (выбросить). Над списком git печатает подсказку по всем командам. Сохраните, выйдите, и git начнёт переигрывать; на каждом `reword` и `squash` он откроет редактор для сообщения.

<details>
<summary>Подсказка 1: порядок строк</summary>

Коммит «oops» чинит то, что сделано в «read key=value lines», значит, его строку надо передвинуть сразу под неё и пометить `fixup`. Два «wip» и «skip blank lines too» это одна работа про комментарии и пустые строки: первый из них оставить `pick` с `reword`, остальные два `fixup` под ним. «fix typo in README» самостоятелен, его можно поставить куда угодно, хоть первым.

</details>

<details>
<summary>Подсказка 2: squash или fixup</summary>

Оба склеивают коммит с предыдущим. `squash` открывает редактор и предлагает объединить оба сообщения, `fixup` молча оставляет сообщение верхнего. Когда нижний коммит называется «oops», выбор очевиден.

</details>

<details>
<summary>Подсказка 3: посреди rebase что-то пошло не так</summary>

`git status` скажет, на каком шаге вы и что git от вас ждёт. Если хочется начать заново, `git rebase --abort`. Если rebase уже завершён, а результат не нравится, `git reset --hard before-cleanup` и повторить.

</details>

<details>
<summary>Подсказка 4: как переставлять строки в nano</summary>

Ctrl+K вырезает текущую строку, Ctrl+U вставляет её в позицию курсора. В vim это `dd` и `p`. Если редактор совсем мешает, можно открыть список в любом графическом редакторе: `git config --global core.editor "code --wait"` для VS Code.

</details>

**Как понять, что готово.** `git diff before-cleanup feature` не выводит ничего. `git log --oneline main..feature` показывает три строки, и ни одна не называется «wip» или «oops». `bash test.sh` проходит. Закладку оставьте: по ней удобно показать ревьюеру «до и после». `bash check.sh`: раздел 3 без красного.

## 4. Откат опубликованного коммита — `undo/`

**Зачем.** Если сломавший всё коммит ещё только у вас, его можно просто стереть. Но если он уже на сервере и его успели забрать другие, стирать нельзя: у них история останется старой, и при следующем `pull` всё перепутается. Для опубликованного есть `revert`: новый коммит, который делает изменения старого наоборот. История при этом честно показывает и ошибку, и её исправление.

**Ситуация.** `undo/` это клон репозитория `undo-origin.git`, который лежит рядом и играет роль GitHub: в него можно по-настоящему пушить. На `main` пять коммитов, и `bash test.sh` на вершине падает на проверке среднего. Кто-то «ускорил» вычисление, и среднее стало целым.

**Что должно получиться.** Виновный коммит найден, его изменения отменены коммитом revert, тесты проходят, результат отправлен в origin.

**Как подступиться.** Прочитайте `git log --oneline` и найдите подозрительное сообщение. Убедитесь командой `git show <хеш>`: в диффе должна быть видна замена `/` на `//`. Можно подойти с другой стороны: `git blame stats.py` показывает для каждой строки, какой коммит её последним трогал, и у строки со средним будет стоять нужный хеш. Когда виновник найден, `git revert <хеш>`: git сделает новый коммит с готовым сообщением «Revert ...», которое можно оставить как есть. Запустите тесты и отправьте результат: `git push`.

<details>
<summary>Подсказка 1: почему не reset --hard</summary>

Попробуйте мысленно: `git reset --hard HEAD~2` уберёт и виновника, и коммит про README. Но origin эти коммиты уже знает, и `git push` откажется их «забывать» (сообщение про non-fast-forward). Заставить его можно только силой, а сила ломает историю всем, кто её уже забрал. Поэтому для опубликованного revert, для своего reset.

</details>

<details>
<summary>Подсказка 2: blame прицельно</summary>

`git blame -L '/mean/,+1' stats.py` показывает только строку, в которой встречается `mean`, вместе с хешем и автором.

</details>

<details>
<summary>Подсказка 3: как убедиться, что push прошёл</summary>

`git status -sb` в первой строке показывает `main...origin/main`; если после имени нет `[ahead N]`, всё отправлено. Можно и так: `git log origin/main --oneline -1` должен совпадать с `git log --oneline -1`.

</details>

**Как понять, что готово.** `bash test.sh` даёт пять галочек, `git log --oneline -3` начинается с «Revert», `git status -sb` не показывает `ahead`. `bash check.sh`: раздел 4 без красного.

## 5. Вернуть удалённый файл — `undo/`

**Зачем.** Файл пропадает тремя способами, и у каждого своя степень тяжести: его стёрли на столе, его стёрли и уже положили в коробку, его стёрли коммитом неделю назад. У git есть ответ на все три, и важно распознать, с которым вы имеете дело. Распознаётся это, как обычно, по `git status`.

**Ситуация.** Первые два случая вы устроите себе сами, третий уже в истории: в репозитории когда-то был генератор случайных чисел `gen.py`, и его удалили коммитом «remove gen.py: tests use a fixed sample». Теперь он снова нужен.

**Что должно получиться.** Все три файла на месте, `gen.py` возвращён коммитом и отправлен в origin, `python3 gen.py 5 1` печатает пять чисел.

**Как подступиться.** Уровень первый: удалите README руками, `rm README.md`, и посмотрите `git status`. Git видит удаление как незакоммиченное изменение и в той же строке подсказывает команду, которой его отменить. Выполните её, файл вернётся из коробки.

Уровень второй: удалите тест командой git, `git rm test.sh`, и снова `git status`. Теперь удаление лежит в коробке, и подсказка в `status` другая: сначала вынуть из коробки, потом вернуть на стол. Это два шага, или один с двумя флагами.

Уровень третий: `gen.py` нет ни на столе, ни в коробке, ни в последнем коммите, он есть только в прошлом. Найдите коммит, который его удалил: `git log --oneline -- gen.py` показывает историю пути, даже если файла больше нет. Файл в последний раз существовал в родителе этого коммита, и на родителя можно сослаться как `<хеш>^`. Достаньте файл оттуда на стол, посмотрите на него, затем `add`, `commit` с сообщением вроде `restore gen.py: needed for stress tests` и `push`.

<details>
<summary>Подсказка 1: команда для третьего уровня</summary>

`git restore --source=<хеш>^ -- gen.py` берёт файл из указанного коммита и кладёт на стол. Старый синоним, который тоже встретится вам в интернете: `git checkout <хеш>^ -- gen.py`, он кладёт файл сразу и на стол, и в коробку.

</details>

<details>
<summary>Подсказка 2: посмотреть, не доставая</summary>

`git show <хеш>^:gen.py` печатает содержимое файла из того коммита, не трогая стол. Двоеточие отделяет коммит от пути внутри него.

</details>

<details>
<summary>Подсказка 3: файл удалили в другой ветке</summary>

Здесь не тот случай, но на будущее: `git log --all -- путь` ищет по всем веткам, а `--diff-filter=D` оставляет только коммиты, в которых путь был удалён.

</details>

**Как понять, что готово.** `git status` чист, `ls` показывает все четыре файла, `git log --oneline -1` это ваш коммит про восстановление, и он уже в origin. `bash check.sh`: раздел 5 без красного. Первые два уровня следов в истории не оставляют, так что он видит только третий; первые два вы делаете для себя, и стоит запомнить, что в каждом случае подсказывал `git status`.

## 6. Отложить незаконченное — `undo/`

**Зачем.** Вы на середине правки, и вдруг надо посмотреть другую ветку или срочно что-то починить. Коммитить полуфабрикат не хочется, терять его тоже. Для этого есть `stash`: стол фотографируется в сторонку и очищается, а потом возвращается как был.

**Ситуация.** В `undo/` кроме `main` есть ветка `wip`, в которой кто-то экспериментирует с гистограммой в том же `stats.py`. Вы стоите на `main`.

**Что должно получиться.** Вы начали правку на `main`, сходили на `wip`, посмотрели, вернулись, и ваша правка на месте.

**Как подступиться.** Добавьте в начало `stats.py` строку комментария, например `# TODO: wire in the histogram`, и не коммитьте. Попробуйте `git switch wip`. Git откажется и объяснит, почему: `stats.py` на `wip` другой, и переключение затёрло бы вашу правку. Выполните `git stash`, убедитесь, что `git status` чист, переключитесь на `wip`, посмотрите `git log -1` и конец файла. Вернитесь на `main` и выполните `git stash pop`: правка снова на столе, `git stash list` пуст. Решите, что с ней делать: закоммитить или выбросить (`git restore stats.py`).

<details>
<summary>Подсказка 1: а если switch разрешил переключиться</summary>

Git пускает с грязным столом, когда изменённые файлы одинаковы в обеих ветках: тогда правки просто переезжают вместе с вами. Отказ возникает именно потому, что `stats.py` различается на `main` и `wip`. Если вы правили другой файл, повторите с `stats.py`.

</details>

<details>
<summary>Подсказка 2: что лежит в stash</summary>

`git stash list` показывает все отложенные столы, `git stash show -p` дифф последнего. Новые, ещё не добавленные файлы `stash` по умолчанию не берёт; для них `git stash -u`.

</details>

**Как понять, что готово.** Ваша строка в `stats.py` вернулась после `pop`, `git stash list` ничего не печатает, вы на `main`. `bash check.sh`: раздел 6 без красного (он найдёт и переходы в reflog, и сам отложенный снимок среди объектов `.git`).

## 7. Чистый status: `.gitignore` — `undo/`

**Зачем.** `git status` полезен только пока он короткий. Как только в нём поселяются собранные бинарники, кеши и выводы тестов, настоящие изменения теряются среди мусора, и рано или поздно мусор попадает в коммит. `.gitignore` это список того, что git должен не замечать.

**Ситуация.** `bash test.sh` в `undo/` складывает вывод в каталог `out/`. После первого запуска `git status` показывает его как неотслеживаемый.

**Что должно получиться.** Файл `.gitignore` в корне репозитория, после которого `git status` молчит про `out/`, закоммичен и отправлен в origin.

**Как подступиться.** Запустите тесты, посмотрите `git status`. Создайте `.gitignore` с одной строкой `out/` и снова `git status`: каталог исчез, зато появился сам `.gitignore`, его и коммитим. Проверить, какое правило прячет конкретный файл, можно командой `git check-ignore -v out/actual.txt`. Подумайте, что ещё стоит добавить на будущее, исходя из того, чем вы пользуетесь: `__pycache__/` и `*.pyc` для Python, `a.out` и `*.o` для C++, `.DS_Store` на macOS, каталоги `.idea/` и `.vscode/` от редакторов. Этот же список пригодится в задаче 9 для вашего hw-репозитория.

<details>
<summary>Подсказка 1: файл уже закоммичен, а теперь его надо игнорировать</summary>

`.gitignore` действует только на неотслеживаемые файлы. Если файл уже в альбоме, его сначала убирают из коробки, оставив на столе: `git rm --cached файл`, и коммитят это удаление.

</details>

<details>
<summary>Подсказка 2: синтаксис шаблонов</summary>

`out/` означает каталог `out` на любой глубине, `/out/` только в корне, `*.o` все файлы с таким расширением, `!keep.o` исключение из предыдущего правила. Строки с `#` комментарии.

</details>

**Как понять, что готово.** После `bash test.sh` команда `git status --short` ничего не печатает; `git check-ignore -v out/actual.txt` показывает строку из вашего `.gitignore`; коммит в origin. `bash check.sh`: раздел 7 без красного.

## 8. Pull request в общий репозиторий

**Зачем.** До сих пор вы работали с git в одиночку. Настоящая цель всего этого хозяйства в том, чтобы несколько человек могли менять один проект, не мешая друг другу и проверяя работу друг друга. Механика у этого одна на всю индустрию: fork, ветка, pull request, ревью, исправления, слияние. Здесь вы пройдёте её целиком, включая самый неприятный момент, когда `main` уехал вперёд, пока ваш PR ждал ревью.

**Ситуация.** В организации курса есть репозиторий `course-itl/toolbox`, коллекция инструментов участников курса. Писать в него напрямую нельзя, только через PR. Внутри каталог `tools/`, в нём по подкаталогу на человека и общий `tools/README.md` со списком инструментов.

**Что должно получиться.** Ваш инструмент (stress.sh с прошлой недели или одна из разминок на Python) лежит в `tools/<логин>/` с коротким README, ваш PR прошёл ревью одноклассника, замечания исправлены, ветка перебазирована на свежий `main`, PR слит. Вы, в свою очередь, сделали ревью чужого PR.

**Как подступиться.** Шаг первый, своя копия: на странице `course-itl/toolbox` нажмите Fork. Появится `<логин>/toolbox`, в который вы можете писать. Склонируйте его и добавьте второй remote, указывающий на оригинал:

```bash
git clone git@github.com:<логин>/toolbox.git
cd toolbox
git remote add upstream git@github.com:course-itl/toolbox.git
git remote -v
```

Теперь `origin` это ваш fork, `upstream` оригинал.

Шаг второй, ветка и коммиты. `git switch -c add-<логин>`, положите инструмент и `README.md` в `tools/<логин>/`, добавьте строку про себя в `tools/README.md`. Коммитьте осмысленно: сам инструмент и строка в общем списке могут быть разными коммитами.

Шаг третий, PR. `git push -u origin add-<логин>`: git напечатает ссылку, по которой открывается форма pull request, в ней выберите base `course-itl/toolbox` ветка `main`. Заголовок по сути (`tools: add <логин>/stress.sh`), в описании что это, как запустить и на что смотреть ревьюеру.

Шаг четвёртый, ревью. Преподаватель объявит, кто чей PR читает. Откройте назначенный вам PR, вкладка Files changed, и пройдите по `review-checklist.md`. Комментарии вешайте на конкретные строки, вопросы задавайте как вопросы, в конце Review changes и вердикт: Approve или Request changes. Чтобы запустить чужой инструмент, заберите ветку PR к себе: `git fetch upstream pull/<номер>/head:pr-<номер>` и `git switch pr-<номер>`.

Шаг пятый, ответ на ревью. Правки делайте новыми коммитами в той же ветке (не `--amend`: ревьюеру нужно видеть, что именно изменилось) и просто `git push`, PR обновится сам. На каждый комментарий ответьте, хотя бы «сделано», и нажмите Re-request review.

Шаг шестой, уехавший `main`. Пока PR ждал, преподаватель вольёт в `main` изменение, которое затрагивает `tools/README.md`, и GitHub покажет, что ветка отстала или конфликтует. Притяните свежий `main` и переложите на него свою ветку:

```bash
git fetch upstream
git rebase upstream/main
# если конфликт в tools/README.md: оставить и свою строку, и чужие, git add, git rebase --continue
git push --force-with-lease
```

Сила нужна, потому что rebase сделал новые коммиты, а на сервере лежат старые. `--force-with-lease` вместо `--force` потому, что он откажется, если в вашу ветку тем временем кто-то запушил, и ничего не затрёт.

Шаг седьмой, после слияния: `git switch main`, `git pull upstream main`, `git push origin main`, чтобы fork не отставал.

<details>
<summary>Подсказка 1: запутался в remote</summary>

`git remote -v` показывает, какое имя куда указывает. `git branch -vv` показывает, за какой удалённой веткой следит каждая локальная. `git log --oneline --graph --all` показывает и `origin/*`, и `upstream/*`.

</details>

<details>
<summary>Подсказка 2: force-with-lease отказал</summary>

Значит, на сервере в вашей ветке есть что-то, чего нет у вас: вероятно, вы пушили с другой машины или с сервера курса. `git fetch origin` и посмотрите `git log origin/add-<логин>`, прежде чем решать.

</details>

<details>
<summary>Подсказка 3: есть gh</summary>

Если на машине есть GitHub CLI, `gh pr create` открывает PR из терминала, `gh pr checkout <номер>` забирает чужой PR для проверки, `gh pr view --web` открывает его в браузере.

</details>

**Как понять, что готово.** Ваш PR в состоянии Merged, в его истории видны коммиты после ревью, последний push был после rebase. На чужом PR есть ваше ревью с комментариями и вердиктом. Всё это преподаватель снимает с GitHub скриптом, пересказывать не нужно.

## 9. Сдача через PR в свой репозиторий

**Зачем.** С этой недели так сдаётся всё. Сдача через PR значит, что работа ждёт в отдельной ветке, пока её не прочитают, замечания исправляются до слияния, а `main` всегда содержит только принятое.

**Что должно получиться.** В вашем hw-репозитории PR из ветки `03-git` в `main`, одобренный ревьюером и слитый вами. В нём `README.md` в корне репозитория и `.gitignore` в корне.

**Как подступиться.** В клоне hw-репозитория `git switch -c 03-git`. Напишите корневой `README.md`: кто вы, что это за репозиторий, как устроены каталоги, как запустить проверки прошлых недель. Соберите `.gitignore` из того, что вы обсуждали в задаче 7. Это два разных изменения, и коммитов тоже лучше два. Отправьте ветку (`git push -u origin 03-git`) и откройте PR; ревьюера преподаватель назначит и даст ему доступ к вашему репозиторию на эту неделю. После Approve нажмите Merge pull request, затем у себя `git switch main`, `git pull`, `git branch -d 03-git`.

<details>
<summary>Подсказка: что писать в описании PR</summary>

Коротко, что внутри и на что ревьюеру обратить внимание.

</details>

**Как понять, что готово.** На GitHub PR в состоянии Merged, у вас локально `main` содержит новые `README.md` и `.gitignore`. Состояние PR преподаватель снимает с GitHub тем же скриптом, что и в задаче 8.

## Bonus

### B1. Бинарный поиск по истории — `bisect/`

Сорок коммитов, в последнем `bash test.sh` падает, в первом проходит. Читать сорок диффов долго; `git bisect` делит историю пополам и за шесть проверок находит виновника. Сначала руками: `git bisect start`, `git bisect bad HEAD`, `git bisect good <хеш первого коммита>` (его даёт `git rev-list --max-parents=0 HEAD`), затем на каждой остановке запускать тест и отвечать `git bisect good` или `git bisect bad`. Потом автоматически: `git bisect reset`, и всё то же самое, но вместо ручных ответов `git bisect run bash test.sh`, потому что тест возвращает код 0 или 1, а это ровно то, что bisect понимает. Когда виновник найден, сохраните журнал, прежде чем выходить из режима поиска: `git bisect log > bisect.log`, и только потом `git bisect reset`. Файл остаётся в `bisect/`, по нему `check.sh` видит и виновника, и число шагов. Подумайте, как в роль `test.sh` здесь встал бы ваш `stress.sh`: `bisect run` принимает любую команду, лишь бы она отвечала кодом выхода.

### B2. Машина времени — `undo/`

Выполните `git reset --hard HEAD~3` и посмотрите на `git log`: три коммита исчезли. Теперь `git reflog`: дневник, где был HEAD, показывает хеш до reset. Вернитесь на него (`git reset --hard HEAD@{1}` или по хешу). Затем удалите ветку `wip` командой `git branch -D wip` и воскресите её из reflog: `git branch wip <хеш>`. Выводы: когда коммиты по-настоящему теряются, а когда нет. Следы обеих операций остаются в reflog, по ним `check.sh` и зачтёт бонус.

### B3. Обжить git

Алиас для графа: `git config --global alias.graph "log --oneline --graph --all --decorate"`. Глобальный список игнорирования для личного мусора вроде `.DS_Store` и `.idea/`: файл `~/.gitignore_global` и `git config --global core.excludesFile ~/.gitignore_global`. Имя ветки в приглашении shell: для bash функция `__git_ps1` из `git-prompt.sh`, для zsh `vcs_info`, или готовый [starship](https://starship.rs/). Покажите на уроке, что получилось.

### B4. Learn Git Branching

Раздел Remote целиком: `clone`, `fetch`, `pull`, `push`, `pull --rebase`, и уровни про расходящуюся историю. Это те же задачи 2 и 8, но на картинках и без последствий.

### B5. Git-гольф

Преподаватель покажет распечатку `git log --oneline --graph --all` небольшой истории с ветками и слиянием. Воспроизведите такую же форму в пустом репозитории за минимум команд. Считаются все команды git; побеждает самый короткий список, который даёт ту же картинку.
