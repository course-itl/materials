# Неделя 3 — Git: альбом снимков, а не заклинания

Две недели вы пользовались git как ритуалом: `status`, `add`, `commit`, `push`, и пока всё шло гладко, этого хватало. Ритуал ломается в первый же момент, когда что-то идёт не так: файл пропал, коммит ушёл не туда, двое правили одну строку, и терминал выдаёт три абзаца текста, из которых понятно только слово «error». В такой момент человек, который знает заклинания, гуглит и копирует чужую команду, не понимая, что она сделает. Человек, который знает модель, читает сообщение git и видит в нём подсказку, потому что git почти всегда говорит, что делать дальше.

На лекции вы видели эту модель изнутри: что лежит в `.git`, как устроен коммит, почему ветка весит сорок байт. В этом README она пересказана совсем на пальцах, чтобы её было легко вспомнить через месяц. А дальше, в `tasks.md`, вы будете ломать и чинить подготовленные репозитории, пока руки не запомнят, что делать в каждой из типовых ситуаций. С этой недели любая работа сдаётся через pull request с ревью, и это тоже часть тренировки.

## О чём была лекция, на пальцах

### Снимок, а не список изменений

Представьте, что git это фотоальбом вашего проекта. Каждый коммит это фотография всей папки целиком, со всеми файлами, какими они были в этот момент. Не «что изменилось с прошлого раза», а именно вся папка. К фотографии приклеена подпись: кто снимал, когда, зачем (это сообщение коммита) и стрелка на предыдущую фотографию, с которой эта выросла.

Если открыть фотографию, внутри три вида деталей. **Blob** это содержимое одного файла, просто байты, без имени. **Tree** это папка: список строк «имя → blob или другой tree». **Commit** это карточка, на которой написано «корневая папка такая-то, родитель такой-то, автор, дата, сообщение». Вот и вся структура данных. Всё остальное, что умеет git, это операции над ней.

### Имя — это отпечаток содержимого

У фотографий нет номеров, у них есть отпечатки пальцев. Имя каждого объекта это хеш его содержимого: сорок шестнадцатеричных символов, которые вы видите в `git log`. Из этого следуют две вещи, которые объясняют половину поведения git. Первая: одинаковое содержимое получает одинаковое имя, поэтому файл, который не менялся сто коммитов подряд, хранится один раз, а не сто. Вторая: изменить объект нельзя в принципе, ведь изменится содержимое, а значит и имя, и это будет уже другой объект. В альбом можно только добавлять. Когда вы «исправляете» коммит (`--amend`, `rebase`), git делает новый коммит и перестаёт показывать старый, но старый ещё какое-то время лежит в альбоме. На этом стоит `reflog` и вся «отмена отмены».

### История — это граф со стрелками назад

Коммиты показывают на родителей, а не на детей, как в семейном древе, если смотреть на него снизу вверх: каждый знает, от кого произошёл, но не знает, кто произойдёт от него. Обычно у коммита один родитель, и история выглядит как цепочка. Когда две цепочки сливают, появляется коммит с двумя родителями, merge-коммит, и граф становится похож на реку с притоком. `git log --graph` рисует ровно эту картинку, и читать её стоит научиться в первый же день.

### Ветка — это стикер

Ветка не копия проекта и не папка. Ветка это бумажный стикер с названием, наклеенный на один коммит. Когда вы делаете новый коммит, стикер той ветки, на которой вы стоите, переклеивается на него. Создать ветку значит приклеить ещё один стикер на тот же коммит, поэтому это мгновенно и бесплатно. Удалить ветку значит оторвать стикер; коммиты при этом никуда не деваются.

Есть один особый стикер, **HEAD**, «вы находитесь здесь». Обычно он приклеен не на коммит, а на другой стикер, на ветку, и тогда новые коммиты двигают эту ветку. Если приклеить HEAD прямо на коммит (`git checkout <хеш>`), git скажет «detached HEAD»: вы здесь, но ни одна ветка за вами не идёт, и коммиты, сделанные в таком состоянии, легко потерять, если не наклеить на них стикер.

### Три зоны: стол, коробка, альбом

Между вашими файлами и альбомом есть промежуточная станция, и именно она сбивает с толку новичков. **Рабочая папка** это стол, на котором вы работаете. **Индекс** (он же staging area) это коробка, куда вы складываете то, что попадёт на следующую фотографию. **Репозиторий** это альбом. `git add` кладёт файл в коробку; `git commit` фотографирует коробку, а не стол. Коробка нужна, чтобы снимать не всё, что лежит на столе: исправили баг и заодно добавили отладочный print, значит, в коробку идёт только исправление. `git status` показывает все три зоны сразу, и его стоит читать целиком, а не только первую строку.

### Слить или переложить: merge и rebase

Когда две ветки разошлись, есть два способа собрать их вместе. **Merge** завязывает узел: появляется коммит с двумя родителями, и история честно показывает, что работа шла параллельно. **Rebase** перекладывает ваши фотографии поверх чужих: git берёт ваши коммиты, по одному заново накладывает их на конец другой ветки и получает новые коммиты с новыми отпечатками, а старые остаются сиротами. История после rebase выглядит как прямая линия, будто вы начали работу позже, чем на самом деле. Оба способа дают одинаковое содержимое файлов, различается только форма графа. Правило простое: свою ещё не опубликованную ветку можно перекладывать сколько угодно, а то, что уже увидели другие, только сливать.

### Конфликт — это вопрос, а не ошибка

При слиянии git сам совмещает правки в разных местах файла. Если же обе стороны изменили одни и те же строки, у git нет способа узнать, чья версия правильная, и он спрашивает вас. Вопрос записан прямо в файл, маркерами: между `<<<<<<<` и `=======` одна версия, между `=======` и `>>>>>>>` другая. Ваша работа не выбрать одну из них, а написать ту, которая должна быть, часто это смесь обеих, после чего убрать маркеры, проверить, что всё работает, и сказать git `add` и `commit` (или `rebase --continue`). Если стало страшно, `git merge --abort` возвращает всё, как было до попытки.

### Другие альбомы: remote, fork, pull request

На GitHub лежит ещё один альбом, копия вашего, и git зовёт его `origin`. `git clone` делает копию чужого альбома себе; `git fetch` приносит оттуда новые фотографии и сообщает, где у них стоят стикеры (их вы видите как `origin/main`); `git push` относит ваши. `git pull` это `fetch` плюс `merge` одной командой. Когда у вас нет права писать в чужой альбом, вы делаете **fork**, свою копию на GitHub, работаете в ней, а потом открываете **pull request**: «посмотрите мои фотографии и, если всё хорошо, возьмите их к себе». Pull request это и есть место, где происходит ревью кода.

### Отменить — значит добавить

Поскольку в альбом можно только добавлять, у «отмены» несколько разных смыслов, и важно не перепутать. `git restore файл` возвращает файл со стола к версии из коробки или из альбома, это отмена незакоммиченных правок. `git reset` переклеивает стикер ветки на другой коммит, так убирают свои ещё не опубликованные коммиты. `git revert` делает новый коммит, который отменяет изменения старого, и это единственный честный способ откатить то, что уже видели другие. А `git reflog` это дневник, куда HEAD ходил последние недели: даже после самого неудачного `reset --hard` там лежит хеш, с которого всё можно вернуть.

### Шпаргалка: команда и что она делает со стикерами

| Команда | Что происходит в модели |
|---|---|
| `git add f` | файл со стола копируется в коробку |
| `git commit` | коробка фотографируется, стикер текущей ветки и HEAD переезжают на снимок |
| `git switch b` | HEAD переклеивается на стикер `b`, стол перекладывается под него |
| `git branch b` | новый стикер `b` на текущий коммит, больше ничего |
| `git merge b` | новый снимок с двумя родителями (или просто переезд стикера, если можно) |
| `git rebase b` | ваши снимки переделываются поверх `b`, стикер ветки едет на копии |
| `git reset --hard X` | стикер ветки и HEAD на `X`, стол и коробка приводятся к `X` |
| `git revert X` | новый снимок, в котором изменения `X` сделаны наоборот |
| `git restore f` | файл на столе заменяется версией из коробки |
| `git stash` | стол фотографируется в сторонку и очищается |
| `git fetch` | новые снимки с сервера, стикеры `origin/*` обновляются |
| `git push` | ваши снимки на сервер, стикер там переезжает |

## Как устроена неделя

Весь тренажёр живёт в одном скрипте. Команда `bash setup.sh` собирает в `~/git-practice/` пять маленьких репозиториев с заранее подготовленной историей: в одном лежит незакоммиченная каша из трёх правок, в другом две ветки, которые конфликтуют, в третьем неряшливая ветка из шести коммитов, в четвёртом «удалённый» репозиторий, в который можно по-настоящему пушить, в пятом сорок коммитов, один из которых что-то сломал. Ломать их можно безжалостно: `bash setup.sh --reset` возвращает всё в исходное состояние. Скрипт работает и на ноутбуке, и на сервере курса (`bash /opt/course/materials/03-git/setup.sh`).

Задачи лежат в `tasks.md`. Каждая начинается с того, зачем это нужно, описывает ситуацию и то, что должно получиться в конце, предлагает путь и прячет подсказки под спойлерами: сначала попробуйте сами, подсказку открывайте, когда застряли минут на пять. В конце каждой задачи написано, как самому убедиться, что готово. Формально это делает второй скрипт, `check.sh`: он читает историю, reflog и содержимое репозиториев тренажёра и для каждой задачи говорит, сделана ли она, а если нет, то что не так. Отчёт по шаблону `report-template.md` поэтому короткий: вывод `check.sh` и несколько вопросов, на которые нужно ответить словами.

Задачи идут в разумном порядке, от одного файла к работе с другими людьми, но жёсткой привязки к урокам нет: делайте в своём темпе, на уроках преподаватель ходит между столами и разбирает затыки на проекторе.

## Что сдаётся (core)

1. **Pull request в ваш hw-репозиторий** из ветки `03-git` в `main`. В нём `03-git/report.md` (вывод `check.sh` без красного по задачам 1–7 и ответы на вопросы шаблона), `README.md` в корне репозитория (кто вы, что здесь лежит, как запускать проверки) и `.gitignore` в корне. PR должен быть одобрен ревьюером, после чего вы его сливаете сами.
2. **Pull request в `course-itl/toolbox`** с вашим инструментом (stress.sh или одна из разминок прошлой недели), доведённый до слияния: замечания ревьюера исправлены, ветка перебазирована на свежий `main`.
3. **Ваше ревью** чужого PR в `toolbox` по `review-checklist.md`: хотя бы два содержательных комментария и вердикт.

Проверка устроена так: задачи 1–7 проверяет `check.sh`; состояние PR (слит ли, было ли ревью, были ли исправления и rebase после него, ваше ревью чужого PR) преподаватель снимает с GitHub скриптом; ответы на вопросы отчёта читает ревьюер.

## Bonus (по желанию, к «отлично»)

- **Бинарный поиск по истории** (`bisect/`): найти среди сорока коммитов тот, что сломал тест, не читая их все; `git bisect run` с тестом как оракулом. Если ваш `stress.sh` прошлой недели возвращает код ошибки при найденном контртесте, он тоже годится в оракулы.
- **Машина времени**: сделать себе `git reset --hard HEAD~3` в `undo/` и вернуть всё через `reflog`; удалить ветку `wip` и воскресить её.
- **Обжить git**: алиас `git graph`, удобный `core.editor`, глобальный `.gitignore`, имя ветки в приглашении shell.
- **learngitbranching**: уровни про remote (`origin`, `fetch`, `pull`, `push`, rebase на удалённую ветку).
- **Git-гольф**: по распечатанному `git log --graph` воспроизвести такую же форму истории в пустом репозитории за минимум команд.

## Правила недели

- `git push --force` в `main` не делает никто и никогда. `--force-with-lease` допустим только в собственную ветку собственного PR, после rebase.
- Застряли: сначала прочитать `git status` целиком, там почти всегда написано, что делать. Потом `git reflog`. Потом сосед, потом преподаватель. Сломали тренажёр безнадёжно: `bash setup.sh --reset`.
- Сообщения коммитов по-английски, в настоящем времени, о сути: `stats: survive empty input`, а не `fix` и не `wip` (вы увидите в задаче 3, во что превращается ветка из таких коммитов).
