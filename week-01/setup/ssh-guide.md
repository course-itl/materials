# SSH на сервер курса

У курса есть общий Linux-сервер. На нём: единое окружение (одинаковое у всех, в отличие от ваших ноутбуков), автопроверка заданий, позже — профилирование (нед. 7) и деплой ваших сервисов (3-я четверть). Логин вам выдаёт преподаватель на уроке 4.

Адрес сервера: `89.169.167.34`.

## 0. Как это вообще работает

Проблема: терминал у вас в руках, а компьютер, на котором надо работать, — в дата-центре за тысячу километров. SSH (**s**ecure **sh**ell) решает её буквально по имени: на сервере запускается самый обычный shell (глава 1 — тот самый собеседник), а ваш терминал подключается к нему по сети. Каждая набранная строка уезжает на сервер, каждый ответ приезжает обратно; всё по дороге зашифровано. Модель «строки туда — строки обратно» из главы 1 здесь окупается сполна: раз интерфейс — просто текст, его можно гонять по проводу, и работа на машине в другом полушарии не отличается от работы на своей.

Осталась одна проблема — **как сервер узнаёт, что вы — это вы**. Об этом следующий раздел.

## 1. Ключи вместо паролей

Пароль — плохой способ доказывать личность машине: его можно подобрать, подсмотреть и выманить, а главное — при каждом входе он летит по сети (пусть и зашифрованным). SSH использует способ лучше — пару ключей:

- **Публичный ключ** — это как замок: его не страшно раздавать кому угодно. Вы вешаете свой замок на любые серверы (и на GitHub — тоже он).
- **Приватный ключ** — единственный ключ к этому замку. Он лежит у вас и **никогда никуда не передаётся**.

При входе сервер даёт вашей машине математическую задачку, решить которую можно только приватным ключом; машина отвечает решением — сам ключ при этом по сети не едет вообще. Перехватывать нечего, подбирать нечего. Поэтому по ключам ходит вся индустрия, а вход по паролю на серьёзных серверах просто выключен (на нашем — тоже).

Сгенерируйте пару (если уже есть — второй раз не нужно):

```bash
ssh-keygen -t ed25519 -C "вашлогин@курс"
# Enter на все вопросы (путь по умолчанию, без passphrase — пока что)
```

Появятся два файла:

- `~/.ssh/id_ed25519` — **приватный**. Не копировать, не пересылать, не коммитить.
- `~/.ssh/id_ed25519.pub` — публичный. Его содержимое отправьте преподавателю:

```bash
cat ~/.ssh/id_ed25519.pub
```

Этот же ключ вы на уроке 5 добавите в GitHub — один ключ обслуживает всё.

Если вы на WSL2: генерируйте ключ в терминале Ubuntu (чтобы он лёг в `/home/вы/.ssh`, а не в Windows-каталог) — иначе ssh будет ругаться на права файла.

## 2. Конфиг, чтобы не печатать адрес каждый раз

Допишите в файл `~/.ssh/config` (создайте, если нет):

```
Host course
    HostName 89.169.167.34
    User вашлогин
    ServerAliveInterval 60
```

Теперь вход — просто:

```bash
ssh course
```

При первом подключении ssh спросит про fingerprint хоста — ответьте `yes`. Что это было: у сервера тоже есть ключ, а fingerprint — его отпечаток. Проверка личности работает в обе стороны: не только сервер проверяет вас, но и ssh проверяет, что вы пришли на *тот самый* сервер, а не на подставной, притворяющийся им. Первый раз отпечаток принимается на веру и запоминается; дальше ssh молча сверяет его при каждом входе — и поднимет тревогу, если сервер вдруг «сменил лицо».

## 3. Копирование файлов: scp

```bash
scp solution.cpp course:week-01/      # с ноутбука на сервер
scp course:week-01/result.txt .       # с сервера на ноутбук
scp -r mydir course:                  # каталог целиком
```

Пути справа от `course:` — относительно вашего домашнего каталога на сервере.

## 4. tmux: сессия, которая не умирает

Проблема: закрыли ноутбук / отвалился Wi-Fi → SSH-сессия оборвалась → всё, что в ней работало, убито. Почему убито, вы знаете из главы 3: ваши команды — дети шелла SSH-сессии, умер родитель — умерли дети.

Решение — tmux. Он разрывает эту цепочку родства: внутри tmux ваши программы — дети tmux-сервера, который живёт на сервере курса сам по себе и от вашей SSH-сессии не зависит. Обрыв связи убивает только «окно», через которое вы смотрели; сама сессия со всеми программами продолжает жить, и к ней можно прицепиться снова — хоть завтра, хоть с другого устройства.

Минимум для жизни:

```bash
tmux                # новая сессия (на сервере, после ssh)
# ... работаете ...
# Ctrl+b, затем d   # отцепиться (сессия продолжает жить)
tmux attach         # прицепиться обратно (хоть завтра, хоть с другого устройства)
tmux ls             # список сессий
```

Привычка курса: зашли по ssh → сразу `tmux attach || tmux`.

## 5. Правила общежития

Сервер общий, на нём вся группа:

- Домашний каталог — ваш; чужие смотреть можно только если вас позвали.
- Не запускайте бесконечные циклы вне лаб по профилированию; заметили, что сервер тормозит — `htop`, найдите виновника (может, это вы).
- Сервер — часть курса, а не полигон для взлома. Найденную дыру в настройке несите преподавателю — это плюс в карму, а не повод для шалостей.

## 6. Жить на сервере целиком

Всё это можно довести до конца: не копировать работу через `scp`, а писать её прямо на сервере, в клоне своего репозитория, и там же проверять и сдавать. Что для этого нужно и как устроен рабочий цикл, описано в `server-guide.md`.
