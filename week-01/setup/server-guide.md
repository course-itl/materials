# Жизнь на сервере курса

Всё, что нужно для курса, на сервере уже стоит: bash пятой версии, `g++`, `python3`, `shellcheck`, `gdb`, `make`, `git`, `tmux`, редакторы `nano` и `vim`. Поэтому работать можно двумя равноправными способами. Первый: писать на ноутбуке и копировать результат на сервер для проверки, как описано в `ssh-guide.md`. Второй: жить на сервере целиком, редактируя файлы там же, где они проверяются и сдаются. Второй способ избавляет от установки инструментов, от разницы между macOS и Linux и от `scp` туда и обратно. Ценой становится привычка к терминальному редактору и зависимость от интернета. Эта страница про второй способ. Всё, что здесь описано, делается один раз; дальше рабочий цикл недели умещается в четыре команды.

## Что где лежит

Материалы курса лежат в `/opt/course/materials`. Это копия того же репозитория, что вы видите на GitHub, она обновляется сама при каждой публикации и открыта только для чтения. Читать учебник удобнее в браузере, а вот копировать заглушки, компилировать выданные решения и запускать скрипты недели удобнее прямо отсюда:

```bash
ls /opt/course/materials/week-02/stress/fixtures/       # заглушки для стенда stress.sh
less /opt/course/materials/week-02/reading/01-scripts.md # можно читать и так
```

Команды курса лежат в `PATH` и запускаются из любого места: `make-quest` создаёт квест недели 1 в `~/quest`, `make-logs` генерирует данные для задач про пайпы в текущем каталоге, а `check-pipes`, `check-stress` и `check-warmups` проверяют работу. `verify-flag` сверяет флаг квеста.

Ваш домашний каталог `~` принадлежит вам. В нём будут жить квест и клон вашего репозитория с домашними работами.

## Свой репозиторий на сервере

Сдача идёт через GitHub, поэтому серверу нужно право пушить в ваш репозиторий. Ключ, которым вы заходите на сервер, лежит на ноутбуке, и сервер им воспользоваться не может. Значит, у сервера должен быть собственный ключ. Это второй ключ, и это нормально: у каждой машины свой.

Шаги те же, что на уроке 5 для ноутбука (`lesson-5-git-start.md`), только выполняются на сервере:

```bash
ssh-keygen -t ed25519 -C "course-server"   # Enter на все вопросы
cat ~/.ssh/id_ed25519.pub                  # этот текст → github.com → Settings → SSH and GPG keys → New SSH key
ssh -T git@github.com                      # "Hi <логин>!" — значит, работает

git config --global user.name "Имя Фамилия"
git config --global user.email "вы@example.com"
git config --global init.defaultBranch main

cd ~
git clone git@github.com:course-itl/hw-<логин>.git   # имя вашего репозитория в организации
```

После этого `~/hw-<логин>` и есть ваше рабочее место на весь год.

## Рабочий цикл недели

Проверки ищут вашу работу сначала в текущем каталоге, потом в `~/hw-<логин>/week-NN`, потом в `~/week-NN`. Поэтому достаточно стоять в каталоге недели и звать проверку без аргументов:

```bash
cd ~/hw-<логин>/week-02
nano stress.sh            # или vim
check-stress              # найдёт ./stress.sh и task-a/counter.txt рядом
check-warmups             # найдёт ./python/
git add week-02 && git commit -m "week-02: stress.sh v1" && git push
```

Для недели 1 так же: из `~/hw-<логин>/week-01` команда `check-pipes` найдёт `solutions/`.

Материалы недели, которые нужны для работы, копируйте из `/opt/course/materials` к себе, а выданные решения компилируйте по полному пути, не таская исходники в свой репозиторий:

```bash
cp /opt/course/materials/week-02/stress/fixtures/*.py ~/stress-lab/
g++ -O2 -std=c++17 -o slow /opt/course/materials/week-02/stress/task-a/slow.cpp
```

Бинарники, временные файлы и каталоги вроде `~/stress-lab` в репозиторий не коммитьте; `git status` перед `git add` покажет, что вы собираетесь добавить.

## Редактор

Для начала хватит `nano`: он показывает подсказки внизу экрана, сохранить `Ctrl+O`, выйти `Ctrl+X`. Кто прошёл `vimtutor` из бонуса недели 1, тому `vim` быстрее. С недели 2 законно и третье: расширение Remote-SSH для VS Code открывает каталог на сервере в привычном редакторе на ноутбуке, а терминал внутри него уже серверный. На неделе 1 это считалось читерством, потому что нужно было прожить неделю в чистом терминале; дальше выбор за вами.

## tmux обязателен

Всё, что живёт дольше минуты, запускайте внутри `tmux`: стресс-тест на тысячу тестов, квест с его процессом-вредителем, длинную сборку. Обрыв Wi-Fi или закрытая крышка ноутбука тогда ничего не убьют, а вернувшись, вы продолжите с того же места. Привычка из `ssh-guide.md` остаётся: зашли по ssh, сразу `tmux attach || tmux`.

## Правила общежития

Сервер один на всю группу, и правила из `ssh-guide.md` здесь важнее, чем для гостя. Вечный цикл в решении, запущенном без `timeout`, съест ядро у всех, поэтому лимит времени в stress.sh не украшение, а вежливость. Свои процессы видно командой `ps -u $USER`, зависший убивается `kill`. Временные файлы кладите через `mktemp`, а не по фиксированным именам в `/tmp`. Домашние каталоги закрыты от других учеников, но не от администратора, поэтому ничего личного на сервере не храните.
